## 1. 现状与目标

- **包格式封闭**：`core/workshop/models.py` 中的 `WorkshopManifestV1` 为 `extra="forbid"`，入口只有 `ui/index.html`；`package_validator._validate_package_file_set` 只接受 `REQUIRED_PACKAGE_FILES` 和图库图片。
- **Registry**：`RegistryModule` 只有模块级的 `official` 标记；`RegistryVersion` 记录 `state`、摘要和权限等字段，没有版本级审核结论。权限沿用封闭校验，且 `RegistryIndex` 中任一条目不合法，整份目录就会校验失败。因此，在 v1 条目中写入旧宿主不认识的权限名，会让旧宿主拒绝整份目录，只能继续使用缓存或快照。
- **安装生命周期**：`core/workshop/installer.py` 已提供以下能力：先暂存再原子替换的 `install_candidate`（带 `after_extract` 钩子）、active/previous/candidate 版本保留与 `_prune_versions`、`set_enabled`，以及 `uninstall(delete_projects)` 和官方模块墓碑。`install_store.py` 的状态文档使用封闭的 schema v1。
- **进程**：`api/app.py` 的 `lifespan` 负责转换器 Worker、清理循环等启动和后台工作，但还没有工坊模块后端的运行时管理；`api/async_jobs.py` 中的任务只存在于内存。可复用的先例有两类：
  - `core/material_process_lifetime.py`：按 pid 加创建时间识别进程，并在父进程退出后清理；
  - `start_all.py`、`scripts/run_vitest.py`：使用带 `KILL_ON_JOB_CLOSE` 的 Windows Job Object。
- **Electron 与 API**
  - `killChild` 在 Windows 上执行 `taskkill /T /F`，在 POSIX 上向进程组发送 SIGTERM；`will-quit` 时调用 `killAllChildren`。
  - `findPython` 使用仓库内的 venv 或 PATH 中的 Python，桌面版不自带解释器。
  - `api_server.py` 默认绑定 `0.0.0.0`，Electron 启动时改为 `127.0.0.1`。只允许本机访问的端点使用 `api/local_origin_guard.py` 中的 `require_local_app_origin`。
- **前端**
  - `contracts.ts` 中的 `WORKSHOP_RPC_METHODS` 和 `capabilities.ts` 中的 `METHOD_PERMISSION` 都是封闭的方法表。
  - `rpcHost.ts` 的 `close()` 会中止所有挂起的请求；普通请求 30 秒超时。
  - `WorkshopFrame` 的 `readyEvents` 要求 `apiVersion` 与宿主版本完全相等。
  - `handoff.image` 先由 `handoffWorkshopPayloadToConverter` 校验，再写入转换器。
  - 工程保存在 IndexedDB 中（`projectStorage.ts`）。
- **SDK**：宿主锁定的 1.0.1 没有后端接口；前序核查也对照了公开 1.0.2 的接口。SDK 源码已另行检出，分支准备见第 8 节。
- **历史场景**：旧去背景分支曾把处理算法接入宿主配置、FileRegistry、SessionStore 和 Worker，说明独立后端运行时的需求来源；本轮不移植这些业务代码，也不以真实去背景模型作为验收条件。

**目标**：纯前端模块的行为保持不变。宿主新增一套通用的模块后端运行时，负责：

- 按模块声明准备依赖与模型；
- 按需启动和停止进程；
- 托管任务与产物；
- 按归属回收资源。

首轮用最小测试后端证明接入契约和生命周期成立，具体业务模块后续独立接入。

## 2. 推荐架构

### 2.1 结构与职责

```text
模块 UI（iframe）
  │ SDK RPC
  ▼
宿主前端处理器
  │ 本机 HTTP
  ▼
后端运行时（宿主 API 进程内）
  ├ 存储：解释器 / 环境 / 模型 / 引用账本
  ├ 任务：状态、输入、产物落盘
  └ 监管 ─控制通道─▶ 模块后端进程（模块环境 + 后端 SDK）
```

宿主只处理通用要素：操作名、JSON 参数、输入/输出文件、进度和错误码。它不了解“去背景”这类具体业务，业务校验和算法都留在模块后端。

从 DSH 借鉴三条原则：

- 能力由模块声明，宿主通过稳定接口把它们组合起来，不为每种业务硬编码流程。
- 进程、任务、依赖引用等每一项运行贡献，都有明确的所有者和撤销路径。
- “已安装”“已启用”“正在运行”分开记录；移除时先撤销运行贡献，再处理依赖。

不引入 Cordis、profile 或 DSH 的包管理机制。

### 2.2 逻辑隔离：按锁内容区分的不可变环境

| 方案 | 判断 |
| --- | --- |
| 所有模块共用一个环境 | 版本冲突会互相污染；卸载时无法判断哪些包可以删 |
| 每个模块一套完整环境 | 隔离最简单，但解释器、推理库和模型会成倍膨胀；不作为默认 |
| 共享基础层加模块叠加层 | 跨层同名包的遮蔽难以预测，卸载时归属不清 |
| **按锁内容区分（推荐）** | 环境键 = 平台 + 解释器小版本 + 规范化后的锁内容。锁相同的模块共用一个环境，锁不同则各自独立，冲突版本自然共存 |

具体做法：

- **环境建成后只读**：多个环境共享物理文件时，这一点尤其必要。临时文件、字节码和常见库缓存（如 `TMP`、`PYTHONPYCACHEPREFIX`、`HF_HOME`、`NUMBA_CACHE_DIR`）重定向到模块私有目录，使运行期写入的内容可归属、可删除。
- **解释器由宿主托管**，按小版本共享。不复用 `findPython` 找到的开发环境，因为用户可能会重建或升级它。首版建议只提供一个小版本，例如 3.12。
- **锁与下载来源**
  - 模块提供带哈希的锁，覆盖它声明支持的平台。锁格式在原型阶段确定，倾向于标准的 `pylock.toml`。
  - 下载来源（包括镜像）可以配置；无论从哪里下载，内容都按哈希校验。
- **分发方式**
  - 首版推荐只用预编译的 wheel：用户无需安装编译工具链，安装结果也可复现。
  - 这是首版的取舍，不是永久的平台限制。确实需要源码构建的依赖，可以在已授权的本机模式下扩展安装流程，并向用户说明所需的工具链。
  - 无论采用哪种方式，下载、安装和构建都在用户授权之后进行。授权前的预览只解析声明和锁，不执行模块代码。
- **安装工具**：首选固定版本的成熟工具（倾向 uv）。宿主以子进程方式调用它，使用宿主私有的配置、缓存和解释器目录，忽略用户的全局配置。
- **可选 GPU 加速**：以 CPU 为基础，模块可声明按需安装的 GPU 依赖变体。CPU 与 GPU 可能需要不同运行库或不兼容版本，兼容性应参与环境选择；相同内容仍尽量复用。具体锁与变体表示方式由实现确定，准备时机见第 3 节。
- **推荐依赖基线**：SDK 仓库可以发布常见推理栈的推荐版本。模块自愿采用即可提高共享率，不做强制要求。

### 2.3 物理去重与回收：先验证成熟工具，不足再补

逻辑隔离决定每个环境能看到哪些包，物理去重决定同样的内容在磁盘上存几份，两者分开处理。

**判定标准**：存储方案是否合格，看原型能否达到以下用户可见的结果：

1. 新模块与已有模块的依赖有重叠时，磁盘增量约等于两者差异的部分；预览中标为“已共享”的占用与实际大致相符。
2. 卸载一个模块，不影响其他模块运行。
3. 最后一个使用者移除后（包括更新后裁剪旧版本），运行时占用回到基线，只剩用户主动保留的内容；反复升级也不会持续累积旧版本残留。
4. 回收不会破坏任何仍被引用的环境。

**首选路径：使用安装工具的私有缓存**

- 环境以硬链接或写时复制的方式从缓存安装，不使用符号链接模式。这样即使清理缓存，也不会破坏已有环境。
- uv 官方提供三种清理方式：整体清理（`uv cache clean`）、按包清理（`uv cache clean <包名>`）和清除未使用的条目（`uv cache prune`），同时说明不应直接修改缓存内部的文件。
- 这些命令以缓存条目为单位，并不了解 Lumina 各模块之间的引用关系。原型需要验证：组合使用这些命令能否达到上述标准——既不会因清理过度而失去后续的共享，也不会因清理不足而留下残留。

**补充路径：宿主自有的内容仓**（仅在首选路径达不到标准时启用）

- 环境装好后，宿主把其中较大的普通文件按 SHA-256 收入 `store/<哈希>`，再把环境中的原文件换成指向该条目的硬链接。
- 当某个条目只剩它自身这一个链接时，即可回收。
- 这种情况下，安装工具的缓存只作为单次事务的临时目录。代价是可能要重新下载本机已有的 wheel，但磁盘占用不会增加。

**两条路径共用的规则**

- **模型**：模型不是 Python 包，始终由宿主按 SHA-256 存放，字节相同即共享。宿主再按模块声明的文件名，把路径提供给后端。
- **引用归属**：环境、解释器和模型的使用者包括 installer 保留的 active/previous/candidate 版本，以及尚未结束的任务；裁剪版本不能提前删除运行中任务所需内容。用户明确保留的模型单独管理。保留工程、原图和结果不应阻止回收已卸载模块的程序依赖。具体账本与回收实现由原型确定。
- **不支持硬链接时**：例如 FAT/exFAT、部分网络盘或跨卷的情况，退回到复制，并如实统计实际占用。
- **Windows 上的删除失败**：某个共享 DLL 正被另一个模块的进程映射时，删除它的另一个链接名可能会失败（此行为待验证）。遇到这种情况，把它记为“待回收”，等相关进程停止或下次启动时重试，并在卸载报告中说明。

### 2.4 进程与任务：由宿主 API 进程拥有

| 方案 | 判断 |
| --- | --- |
| 在宿主进程或 WorkerPool 中导入模块代码 | 模块依赖会进入宿主环境（违背 R6），取消时也难以真正停下原生计算 |
| 模块自带常驻服务，自己管理任务 | 重入查询、退出回收和取消语义都要靠各个模块自己实现 |
| **宿主监管进程并拥有任务（推荐）** | 任务与 iframe、模块进程解耦，由宿主统一回收 |

**监管者**

- 运行时在 `lifespan` 中创建。每个模块的生效版本对应一个监管者。
- 监管者至少能区分以下状态：未运行、启动中、就绪、执行中、停止中、启动失败。
- 后端进程由模块环境中的解释器启动。
- 控制通道首选 stdio，只传有大小上限的 JSON 消息；图片等数据通过任务目录中的文件传递。
- 后端 SDK 负责防止原生库的输出干扰协议；stderr 写入宿主的结构化日志。
- 如果原型表明 stdout 隔离不可靠，就改用继承的专用管道，或带一次性令牌的本机套接字。

**任务**

- 任务落盘保存，包括状态、进度、稳定错误码、输入和产物。
- 任务至少能区分：排队、运行、完成、失败、已取消、已中断。
- 提交时附带客户端生成的幂等键，任务按模块 ID 隔离。
- 输入和产物沿用现有的 64 MiB 二进制上限。
- 依赖准备也走同一套任务机制，不依赖只存在于内存中的 `AsyncJobMiddleware`。

**与 iframe 解耦**

- 任务落盘后，提交请求立即返回任务 ID。
- `rpcHost.close()` 只结束前端的等待，不会取消任务。
- 重新进入模块界面后，列出本模块的任务即可恢复进度或结果。
- 除了正常完成和执行失败，主动中止任务的触发条件有：显式取消、停用模块、卸载模块、退出程序，以及 Registry 撤销该版本。离开页面不在其中。
- 宿主或后端意外退出时，未完成的任务记为“已中断”。

**取消**

- 先发送协作取消请求；超过宽限期仍未结束，就终止该模块的进程树，并把任务记为“已取消”。
- 首版建议每个后端进程同时只执行一个任务，其余任务排队。这样终止进程不会误伤其他任务。

**空闲释放**

- 没有排队或运行中的任务，且持续超过阈值时，停止后端进程。
- 模块界面打开期间可以适当延长阈值，避免交互式精修时反复加载模型。
- 默认阈值由实现确定；模块可以在宿主允许的范围内提出建议值。

**停用、卸载与退出**

这三种情况都会取消该模块排队和运行中的任务，并只停止它自己的进程树，不影响其他模块和转换器 Worker。已经完成的产物按文件生命周期保留。

需要注意：Electron 在 Windows 上用 `taskkill /T /F` 强制结束 API 进程，`lifespan` 的关闭逻辑来不及执行，因此回收不能只依赖关闭逻辑。以下候选机制由原型确认：

- **Windows**：把模块进程放入带 `KILL_ON_JOB_CLOSE` 的 Job Object，写法参照 `start_all.py`。API 进程异常退出时句柄关闭，模块进程随之结束。
- **POSIX**：模块进程留在 API 所在的进程组中，这样 Electron 对进程组的终止也能覆盖它们。定向停止某个模块时，用 psutil 遍历它的进程树。
- **SDK 兜底**：与宿主的连接断开时，后端 SDK 自行退出。
- **启动时核对**：宿主启动时，按 pid 加创建时间清理遗留进程（参照 `core/material_process_lifetime.py`），把未结束的任务标记为“已中断”，并重试待回收项。

**访问边界**

本机进程模式不是操作系统级沙箱，模块代码以用户自己的权限运行。新端点复用现有的保护：要求本机来源（`require_local_app_origin`），并检查：

- 模块是否已启用；
- 授权记录是否有效；
- Registry 是否已撤销该版本（复用 `_verify_registry_runtime_status`）。

### 2.5 审核等级与授权

审核等级只能来自宿主可信的记录（例如经宿主验签的 Registry），并绑定到具体的版本和包内容。包名、清单里的自述和下载渠道，都不能让模块获得审核身份。签名 Registry 按 SHA-256 校验，只能证明包与条目一致，并不等于内容经过了审核。

审核等级分三种：

- **官方**：签名 Registry 把该模块标记为 `official`，并且本地包的 SHA-256 与该版本的条目一致。
- **已审核的社区版本**
  - 现有 Registry 没有版本级的审核结论，因此需要补充一条最简的可信记录，按模块 ID、版本和包 SHA-256 列出审核通过的版本，例如随签名 Registry 一起发布的清单。
  - 具体表示方式由实现选择，但必须保证旧宿主仍能解析 v1 目录。
  - 在这条记录可用之前，社区版本一律按未审核处理。
- **未审核**：其余所有来源，包括普通本地包、GitHub 安装包，以及没有审核记录的 Registry 版本。

**提示**

- 所有等级都展示用途、声明的能力（例如是否需要联网）和新增占用，并注明：声明只用于说明用途，不受系统强制限制。
- 未审核模块额外提示“代码未经审核，将以你的用户权限在本机运行”，并要求用户明确确认。
- 安装时确认一次即可，不另设审批流程。

**授权记录**绑定模块 ID、版本、包的 SHA-256、后端声明摘要和授权时的审核等级。模块安装期间持续有效，卸载时删除。复用规则如下：

- 内容不变时（例如重启，或回滚到仍保留的版本）直接复用。
- 已审核模块更新时，如果声明的能力没有扩大，沿用原授权；如果扩大，需要用户重新确认，用户拒绝则继续使用旧版本。
- 未审核模块的每个新版本都需要重新确认。
- 审核记录被撤回时，按未审核处理，下次启动后端前需要重新确认。
- Registry 把版本标记为 blocked 时，停止该版本的后端并拒绝再次启动，用户数据保留。

## 3. 用户流程与生命周期

每个模块有三个相互独立的状态：

- 安装：未安装 / 准备中 / 已安装 / 失败；
- 启用：启用 / 停用；
- 运行：见 2.4 的监管者状态。

安装或启用都不会启动后端进程。用户流程如下：

1. **预览**：包先通过现有的校验流程，再解析后端声明并展示：
   - 来源和审核等级；
   - 用途和声明的能力；
   - 新增的解释器、依赖和模型的下载量与磁盘占用，并标明其中已在本机共享的部分。可选加速的额外占用单独列出。
2. **授权**：按 2.5 的规则确认。
3. **准备**：作为后台任务执行，可以查询进度，也可以取消。依次完成：
   1. 准备解释器；
   2. 创建环境（包括去重）；
   3. 下载并校验模型；
   4. 后端自检。

   全部成功后才写入引用账本，候选版本才能被激活。任何一步失败，都撤销这次事务新增的内容并说明原因，不留下“装了一半”的状态。
4. **使用**
   - 提交任务时按需启动后端。
   - 切换页面后任务继续执行，工坊管理页显示“后台运行中”，并提供停止入口。
   - 任务完成后，模块 UI 读取宿主保存的 PNG 字节，再调用现有的 `handoff.image` 把图片交给 Lumina。即使后端已经停止，交接照样可以完成。
5. **可选加速**
   - 用户在模块界面或管理页启用加速后，宿主才准备 GPU 变体；CPU 路径始终可用。
   - 加速初始化失败时，回退到 CPU 并说明原因。
   - 关闭加速后，GPU 变体按引用回收。
6. **更新**：新版本沿用现有的候选流程，并预览依赖增量；授权按 2.5 的规则复用或重新确认。旧版本的环境作为回滚目标保留，被裁剪时释放引用。

## 4. 卸载与数据保留

卸载按以下顺序进行：

1. 停止该模块的任务和进程；
2. 由现有的 `uninstall` 事务移除模块代码；
3. 释放引用，回收无人使用的内容；
4. 生成卸载报告。

| 类别 | 默认处理 | 说明 |
| --- | --- | --- |
| 模块代码与运行文件 | 删除 | 沿用现有事务和官方模块墓碑 |
| 解释器、环境、加速运行库及去重存储 | 按引用自动清理 | 无人使用即删除；仍有其他模块使用的保留，并列出使用者 |
| 模型 | 无其他使用者时删除，用户可选择保留 | 保留的模型在存储概览中可见、可单独删除，重装时直接复用 |
| 模块缓存与临时文件 | 删除 | 依赖 2.2 中的写入重定向 |
| 工程 | 保留，用户可选择删除 | 沿用 `uninstall(delete_projects)`；选择删除时，一并清理该模块在 IndexedDB 和 `projects_dir` 中的工程 |
| 原图副本与处理结果 | 保留，用户可选择删除 | 保留的内容在存储概览中可见、可单独删除 |

原图副本、处理结果等内容的日常保留期限，由实现给出合理的默认值，并支持手动清理。最终下载和用户选择保留的数据，不会因进程退出或源会话关闭而丢失。

卸载报告分为四类：

- 已清理：附释放的字节数；
- 仍共享：附正在使用它的模块；
- 已按用户选择保留；
- 未能删除：附原因，以及是否会自动重试。

统计精度由实现决定，但不能把仍被占用的内容算作“已清理”。授权说明中会注明：宿主只能清理自己托管的位置。模块写到其他位置的内容，卸载报告不会声称已经清理。

## 5. SDK、包格式与宿主改动范围

**包格式**

- 只有带后端的包使用清单 v2，纯前端模块继续使用 v1。
- v2 的后端声明包括：
  - `backend/` 下的入口和源码；
  - Python 版本范围；
  - 锁，包括可选的 GPU 变体锁；
  - 模型清单：标识、HTTPS 地址、SHA-256、大小、许可；
  - 用途和声明的能力。
- 包检查器放行 `backend/` 下有大小上限的文本文件。
- 原生二进制只能来自锁中的依赖；模型不打进包里。

**版本与 Registry**

- Workshop API 升一个次版本（例如 1.1.0）。后端模块在 `workshopApi.min` 中声明这个新版本，这样旧宿主的 `select_install_candidate` 会自动把它过滤掉，旧宿主本地安装 v2 包也会明确失败。
- Registry v1 的格式保持不变：
  - 不向 v1 条目写入新的权限名；
  - 后端声明只放在包内，由现有的 `sha256`/`manifestSha256` 绑定；
  - 社区版本的审核记录按 2.5 的要求，以旧宿主能够解析的方式发布。
- 如果以后需要在“发现”页面预先显示依赖体积，再另外发布签名的 v2 索引。
- `install-state.json` 保持 schema v1 不变。授权、引用和任务存放在独立的文档中，避免降级后旧宿主无法读取。

**JS SDK（发布新的次版本）**

- 新增后端任务接口：提交、查询/列出、取消、读取产物、删除。接口名称由实现确定。
- ready 消息上报模块实际需要的最低 API 版本，新能力另行声明，沿用现有 `events` 的做法。这样，没有用到后端的模块在旧宿主上依然可用。
- 新宿主在 `readyEvents` 中接受不高于自身版本的同主版本号。
- 宿主锁定的 SDK 版本和 `scripts/verify_workshop_release_chain.py` 需要同步更新。

**Python 后端 SDK（新增）**

- 沿用 JS SDK 的不可变 Release 发布方式。
- 提供：握手、任务上下文、进度上报、取消检查、稳定错误码、控制通道保护，以及与宿主断开后自动退出。

**宿主 Python 侧**

- `models.py`、`constants.py`、`package_validator.py` 支持清单 v2。
- `installer.py`：
  - 在候选安装时接入后端准备；
  - 停用或卸载前先停止运行时；
  - 裁剪版本时释放引用。
- `core/workshop/` 下新增运行时子模块，负责存储与回收、进程监管和任务存储，具体拆分由实现决定。
- `api/routers/workshop.py` 新增端点：后端状态、任务、产物、依赖准备、存储概览。
- `api/app.py` 在 `lifespan` 中完成启动核对和关闭。
- 旧分支对 `requirements.txt` 的改动不进入主线。

**宿主前端**

- 运行时接入：
  - `contracts.ts`；
  - `runtime/capabilities.ts`：后端方法的使用资格来自后端声明和授权记录，不新增 v1 权限；
  - `runtime/payloadValidation.ts`；
  - `runtime/handlers.ts`；
  - `api/workshop.ts`。
- `WorkshopPanel.tsx` 新增界面：
  - 安装预览；
  - 风险确认；
  - 运行状态与停止入口；
  - 加速开关；
  - 卸载时的数据类别选择和卸载报告；
  - 存储概览。
- 所有新文案写入 `translations.ts`，覆盖产品支持的界面语言。

**适用范围**

- Electron 桌面版完整支持，平台与宿主一致：Windows x64、Linux x86-64、Apple Silicon macOS。
- 源码启动并在本机浏览器中使用时，沿用现有规则：只有浏览器可信的官方模块能打开，因此也只有它们会调用后端。
- 通过局域网或远程访问时，本机来源校验会返回明确的错误。
- 模块帧的防火墙保持不变。
- 本轮不设计具体业务模块的专用离线安装包，扩展方向见第 7 节。

**最小测试后端（运行时 fixture）**

- 只提供握手、可观察进度的短/长任务、主动失败、响应或忽略协作取消、返回测试产物等能力。
- 使用两份合成模块声明验证共享和冲突依赖；不引入去背景算法、真实模型权重或业务编辑界面。
- 图像交接使用合成的透明 PNG 检查 alpha、尺寸和结果生命周期，证明框架可以承载未来图像类模块。

## 6. 分阶段实施与验证

2. **运行时内核**：实现存储与回收、进程监管、任务、端点和启动时核对；先用仓库内的最小测试后端来驱动。

计划中的验证（均尚未运行）：

- **切换页面**：提交任务后卸载 `WorkshopFrame`，任务仍能完成；重新进入后能拿到结果。
- **取消**：使用一个不响应协作取消的测试后端，确认取消后进程树确实结束、没有残留进程。
- **后端停止后交接**：任务完成后停止后端，并关闭或切换来源会话，仍能读取产物并通过 `handoff.image` 交接；PNG 的 alpha 和尺寸正确。
- **共享依赖**：两个模块的锁有重叠时，第二个模块的实际磁盘增量约等于两者差异的部分。使用硬链接时，可以直接比对共享文件的 `st_dev`/`st_ino`。
- **冲突依赖共存**：同一个包的两个不同版本，在各自的环境中都能被正确导入。
- **卸载与回收**
  - 卸载其中一个模块后，另一个模块仍能完成任务；
  - 卸载最后一个使用者后，运行时目录（不含用户选择保留的内容）恢复到基线，不残留环境、缓存条目、解释器、模型或临时文件。
- **数据选择与重装**
  - 默认保留工程、原图副本和处理结果；用户选择删除时，确实删除；
  - 模型的保留或删除与用户的选择一致；
  - 卸载后可以正常重装，并复用保留的模型。
- **可选加速**：只用 CPU 时不下载 GPU 运行库；启用加速后准备 GPU 变体，失败时回退到 CPU；关闭加速后变体被回收。
- **授权**：已审核与未审核模块的提示区分正确；更新时按 2.5 的规则复用或重新确认；被撤销的版本拒绝启动。
- **退出与崩溃**：Electron 正常退出或强制结束 API 后，没有残留的模块进程；下次启动时，未完成的任务被标记为“已中断”，待回收项被清理。
- **兼容性**
  - 运行 `tests/test_workshop_*` 以及 `docs/context/workshop/CONTEXT.md` 中列出的 Vitest 回归测试；
  - 确认拼豆模块 1.0.1 seed 和 1.0.8 的安装、打开、交接行为不变；
  - 确认 Registry v1 仍能被旧宿主的模型正常解析；
  - 在三个桌面平台上手工测试。

## 7. 原型待验证与后续扩展

**需要原型验证的技术点**（由实现判断，不逐项请示）：

1. 成熟工具（倾向固定版本的 uv）的具体用法：私有目录、链接模式、按哈希安装、忽略用户配置、镜像设置；它的官方缓存命令能否达到 2.3 的判定标准；以及锁文件采用哪种格式。
2. Windows 上的几个行为：
   - 一个正被映射的 DLL，能否删除它的另一个硬链接名；
   - 各平台、各文件系统上的文件链接数是否可靠；

4. 模块声明的数据或模型资源能否在共享存储中准备，并被测试后端正确读取与释放；不验证特定业务模型的加载机制。
5. 代表性依赖在各平台的可用性、重复安装的磁盘增量、CPU/GPU 依赖变体的按需准备，以及启动和回收开销。

**后续扩展**：

- 用户已明确先补充通用后端运行时，不继续扩展具体模块需求。首次离线安装包导入和真实业务模块接入放到后续独立范围；本轮不以这些选择阻塞运行时方案。资源已经备齐时的运行与资源获取方式分开设计。
