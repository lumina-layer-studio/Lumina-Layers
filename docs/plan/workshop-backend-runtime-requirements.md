# 创意工坊后端运行时管理需求

日期：2026-11-04。状态：用户已确认需求并授权实现；实现完成后由独立验证确认结果。

## 目标

为创意工坊补充通用后端运行时，让模块能够声明后端、按需运行任务，并将产物交给宿主已有工作流。

补齐可供其他模块复用的后端运行时管理能力，包括安装、按需启停、任务管理、依赖复用和完整卸载。宿主负责通用管理，模块提供业务处理能力。需求描述结果与约束，不预先锁死通信协议、进程结构、SDK 方法名或环境管理工具。

本轮交付范围是通用后端运行时及其跨仓库接入。去背景只是需求起因，不在本轮迁移、实现、发布或验收任何去背景模块；运行时使用最小测试后端验证。首次离线安装等扩展暂不作为实现的前置决策，不继续扩展具体业务模块需求。

跨仓库范围包括宿主、公开 Workshop SDK 和 Registry；涉及工具或资源分发时再评估 Distribution、Launcher 的必要改动。这五个仓库的本地工作分支已准备，具体基点与工作区状态见[方案第 8 节](workshop-backend-runtime-design.md#8-跨仓库工作准备)。

## 已确认的产品决策

- 采用本机进程模式。用户授权后运行模块后端，不把独立进程或虚拟环境宣传为操作系统级强权限沙箱。
- 官方模块和经过审核的社区模块展示所声明的权限及用途；其余来源（包括普通本地包、GitHub 安装包）在同样的权限说明之外增加未审核代码风险提示，并由用户明确确认。
- 审核身份针对实际版本和包内容，不能凭名称或包内的自我声明获得。具体审核记录和授权复用机制由方案设计。
- 用户切换到 Lumina 其他页面、离开模块界面时，已提交的后台任务继续执行；重新进入模块后能够查看进度或结果。后端空闲后释放。
- 明确停用模块或退出程序时停止对应后端及其未完成任务；已经完成的结果按文件生命周期保留。
- 多个后端安装后不能因重复携带 Python、推理库和模型而无谓膨胀。不预设“一模块一套完整虚拟环境”，也不强行把所有模块塞入会互相污染的单一环境。
- 卸载能清理该模块带来的额外依赖和用户选定的数据；仍被其他模块使用的共享资源保留，最后一个使用者移除后应能回收。
- 卸载默认保留工程、原图副本和处理结果，允许用户选择一并删除；不再使用的程序依赖自动清理。日常保留期限由实现提出合理默认，不在本需求中写死。
- 以 CPU 为基础，允许模块提供可选 GPU 加速，相关运行库按需安装，不能让所有用户被动安装完整 GPU 依赖。
- 详细实现给实现模型留出空间。围绕实际使用和维护问题设计，不附加与本次目标无关的防御设施或治理流程。

## 当前代码事实

宿主检查基线：`main@1308c06fc69915e11ead7dbefa0c1e7da11504d0`。

- 宿主锁定 SDK 1.0.1；已核对公开 SDK 1.0.2。现有 `image.pick` 和 `handoff.image` 支持输入图片及交接 PNG；`lifecycle.ready` 只报告页面就绪，`client.close()` 只关闭客户端连接。
- `frontend/src/workshop/contracts.ts`、`runtime/handlers.ts` 和 `runtime/capabilities.ts` 没有后端运行时或处理任务接口。
- `core/workshop/models.py` 的模块入口只有 `ui/index.html`；包检查器只接受现有固定文件集合；新增后端内容需要明确的包和版本演进方案。
- 模块启用、停用、激活、回滚和卸载已有管理路径，见 `api/routers/workshop.py` 与 `core/workshop/installer.py`。
- 当前 iframe 卸载会关闭宿主 RPC 并触发未完成请求的 `AbortSignal`。新任务需要独立于 iframe 连接存活，不能直接把“页面关闭”当成“任务取消”。
- 当前包大小、图片大小、项目存储、配方信封和文件生命周期均有既有约束，见 `core/workshop/constants.py`、`docs/workshop-module-development.md` 及 `docs/context/workshop/CONTEXT.md`。

背景参考：历史分支 `shmx/feat/image-preprocessing-page@bc6fb65e8848465f55c966fce8012f13c79db0c2` 曾将处理算法直接接入宿主配置、会话和 Worker。它说明独立后端管理能力的需求来源，但不是本轮移植对象。真实去背景模型效果和性能也不属于本轮验收。

## 功能需求与验收重点

| 编号 | 需求 | 应观察到的结果 |
| --- | --- | --- |
| R1 | 模块声明自身后端能力，由宿主管理 | 业务能力可以独立维护和发布，宿主不必为每一种业务硬编码一套运行流程。 |
| R2 | 区分安装、启用和运行状态，按需启动、空闲释放 | 安装或启用不等于常驻占用内存；启动失败、运行中和停止状态可辨认。空闲策略由方案建议。 |
| R3 | 后台任务可查询、取消、重入查看 | 切换页面不丢任务；重进页面能恢复进度或结果；取消要确实结束处理，不能仅取消前端等待。 |
| R4 | 停用、卸载和程序退出能回收所管理的进程与资源 | 后台任务和模块启动的相关子进程能够结束，不影响其他模块及主转换器。 |
| R5 | 安装多后端时复用依赖，兼容必要的版本差异 | 相同兼容依赖、解释器和模型不无谓重复存储；不兼容版本可以共存。具体共享或物理去重方式由方案比较。 |
| R6 | 安装与依赖管理不污染宿主开发环境 | 不要求用户逐个手动配置环境；失败能说明原因并恢复到可管理状态，不把半安装当作成功。 |
| R7 | 卸载清楚、完整且尊重共享关系 | 模块专属运行文件及不再需要的额外依赖可移除；共享资源仅在无人使用时清理。模型、缓存、工程、原图/结果等数据可按清楚的类别选择保留或删除。 |
| R8 | 安装增量和卸载回收可理解、可验证 | 用户能了解需要新增的主要依赖/模型及占用；卸载能说明已清理、仍共享、主动保留或未能删除的内容。显示方式和统计精度由实现决定。 |
| R9 | 权限和来源提示符合已确认的本机执行模式 | 审核模块展示权限；未审核模块额外提示风险并确认。授权变化有清楚的处理方式，不假装声明权限已受系统强制限制。 |
| R10 | 处理产物与运行时解耦 | 任务完成后即使停止后端或切换页面，产物仍可读取；图像类测试产物能通过现有 handoff 进入本体并保留 alpha、尺寸。最终下载和用户保留的数据不因进程退出而丢失。 |
| R11 | 兼容现有工坊与部署方式 | 现有纯前端模块保持可用；方案明确 SDK、包格式、Registry 和宿主的兼容演进，以及现有源码启动、Electron 和各平台的适用范围。 |

## DSH 参考方向

参考项目为 [DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness)，官方资料核查于 2026-11-04。

- [架构说明](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)：能力由插件提供，通过稳定接口组合，宿主不因新增业务不断堆积特例。
- [Cordis Primer](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/cordis-primer.md)：注册资源具有相应的撤销行为，生命周期结束时释放自身带来的资源。
- [Plugin Manager](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/boot/plugin-manager/README.md)：区分启用状态与包依赖；移除时先卸载运行中的贡献，再处理包依赖。

借鉴这些原则，不要求引入 Cordis、复刻 DSH 的 profile/配置体系，也不把其 Node/pnpm 机制视为 Python 重依赖去重和磁盘清理的现成答案。

## 方案应交付什么

1. 基于实际代码的推荐架构、关键取舍及适量备选，尤其说明依赖共享/隔离和完整卸载如何同时成立。
2. 模块、宿主和运行时的职责，主要调用流程与生命周期；接口只说明必要契约，不冻结每个字段或类名。
3. 安装、更新、停用、卸载和数据保留的用户可见行为，以及正常失败的处理方式。
4. 当前宿主、公开 SDK、包规范及必要发布资源各自的改动范围；独立业务模块只说明未来接入方式，不安排本轮开发任务。实现阶段可以调整文件拆分。
5. 分阶段工作与有意义的验证，包括：切页继续任务、取消、停止后仍能交接、两个模块共享依赖、冲突依赖共存、卸载一个不破坏另一个、最后引用清理、保留/删除选定数据、卸载后重装。
6. 明确需要真实原型验证的假设和仍影响产品行为的少数问题；普通技术选择由设计和实现模型判断，不逐项向用户请示。
