# 资源检索与服务器衔接

当前采用“现有 Registry + 小型目录索引 + 按需预览和下载”。服务器继续负责发布、身份、权限和文件，Studio 负责快速挑选；GitHub 数据快照与离线包保留相同资料字段。当前规模无需新增搜索服务或账号系统。

## 用户如何找

| 意图 | 操作 |
| --- | --- |
| 找手上的某卷耗材 | 搜包装色号，例如 `10101`；也可搜 `拓竹PLA黑色` |
| 不知道准确名称 | 品牌 → 材质 → 系列／色系，选项显示匹配数量 |
| 找一套 LUT | 选色数，必要时再选原料色系；多种色系必须同时包含 |
| 找某人的记录 | 搜公开作者署名，可与品牌、系列同时输入 |
| 网络不可用 | 转到离线包继续相同关键词与筛选，按项添加 |

品牌、材质、系列、耗材色系、LUT 色数在同一维度多选时取并集，不同维度取交集；LUT 原料色系取交集。计数排除当前维度自身的限制，允许替换或增加同维度选项。缺失资料不臆造，模板规则见 [resource-metadata.md](resource-metadata.md)。

关键词按词同时匹配；完整色号和完整名称优先。预先归一大小写、全角、品牌别名和中英文相邻词，原始名称与地区名称都保留。色号不做近似纠错，避免误配耗材。

## 当前已实现的传输策略

| 场景 | 行为 |
| --- | --- |
| 首次打开耗材目录 | 先取 24 条，不等待完整索引才显示页面 |
| 搜索、打开分类筛选、统计本地已安装云端资源的更新 | 获取当前来源的完整目录元数据；不下载耗材包 |
| 同一面板、同一来源继续搜索 | 完整索引有效期五分钟；先向本机状态接口核对来源范围，再在内存检索 |
| 快速连续输入 | 冷搜索等待 400ms；已有完整索引时直接调度；取消旧页面请求、共享正在构建的索引，旧响应不能覆盖新词 |
| 分类筛选与翻页 | 完整索引可用后在本机完成 |
| 手动刷新 | 清除面板索引和对应后台内存目录缓存，立即向远端重新校验 |
| LUT 目录 | 按 100 条分批补齐元数据，24 张卡片一页；色卡预览仅请求当前页缺少的条目 |
| 下载 | 用户点击安装才获取对应文件；搜索、筛选、看详情不安装 |

索引按来源 URL、频道和凭据范围隔离。来源改变、401 或 403 不使用其他范围的结果；私库凭据不转发给公开备用站。目录断网回退使用已有的应用快照机制，并标记缓存。HTTP 共享缓存不用于私有结果。

目前完整索引保留在面板会话内；切出面板再进入可能重新请求本机目录接口，后台仍有缓存。LUT 手动刷新沿用远端条件请求。不要将这些行为描述成“永不发请求”或“所有资源都已下载”。

## Registry 本地升级

沿用 `Lumina-material-registry`。原服务已有耗材的品牌／材质／校准类型／频道筛选、LUT 的品牌／格式／模式筛选、登录与投稿权限；本轮增加或衔接：

- 耗材、LUT 共用公开字段搜索，覆盖系列、包装色号、公开作者、地区别名和 LUT 槽位资料，精确色号优先。
- 有上限的归一文本缓存，避免每次搜索重复生成整条 JSON 字符串；认证与频道权限仍逐请求检查。
- 目录支持 ETag 条件校验及压缩。客户端校验相同内容时返回 304 空正文；权限检查先于 304。
- LUT 目录与色卡预览分开，沿用修订身份缓存预览；完整 LUT 文件仍按项下载。

这些是本地改动，尚未部署线上。2026-11-15 读取线上接口确认耗材 682 条、LUT 136 条；线上已有 gzip，本次实测未返回 ETag。

当前 Studio 的新增系列／色系／色数组合筛选由小型元数据索引完成，**尚未新增这些维度的远端分页 API**。旧版服务可继续供数据，升级服务则增强其网站/API 搜索及条件传输能力。

## 实测与后续扩展

2026-11-15 本机验收，原始记录在当前任务 scratch 的 `search-performance.json`、`search-transfer.json`、`search-network.json`：

| 测量 | 结果 |
| --- | --- |
| 线上 682 条耗材公开目录 | gzip 140,900 字节，约 138 KiB；JSON 938,052 字节；本次请求 0.665 秒 |
| 本地升级 Registry 的 136 条 LUT 目录 | gzip 47,526 字节；JSON 242,283 字节；再次条件请求 304、正文 0 字节 |
| 682 条耗材索引构建，10 次暖测 | 中位 27.37ms，P95 28.35ms |
| 缓存后搜索＋五维计数，100 次暖测 | 中位 0.85ms，P95 1.38ms |
| 浏览器选 Bambu Lab → PLA → 搜 `10101` | 只新增本机状态请求和健康轮询，无目录请求、无文件下载 |

CPU 测量使用 Node 22 运行实际检索模块，排除 React 渲染与网络耗时；本机网络单次结果不代表国内外所有线路。没有建立伪历史性能基线。

后续扩展以实测为触发条件：压缩元数据超过约 1 MiB、首轮加载明显拖慢，或较低配置设备的搜索＋计数 P95 超过 50ms 时，再将相同查询规则下沉服务器。先增加规范化过滤参数、服务端分页和分类计数，客户端只保留当前页及最近查询；发布／撤回时更新目录版本与索引。再依据真实查询量决定 SQLite FTS 或独立搜索引擎，不一次性引入全部设施。上述阈值是本项目的工程决策，尚未实现自动切换。

上线验收要覆盖：旧客户端、匿名公开频道、已登录私有频道、撤销权限、200→304、内容变更后的200、分页中目录更新、断网缓存和按项下载。现有上传身份与审批流程沿用，不另建账户。

## 参考取舍

采用多维筛选、精确字段优先、可复用索引和 HTTP 条件校验；暂不引入模糊搜索依赖。Fuse.js 的字段权重和索引复用可参考，但包装色号的误匹配成本高，当前优先保持确定匹配。HTTP 条件校验遵循 RFC 9111／If-None-Match 的语义。

- Fuse.js 官方：`https://www.fusejs.io/fuzzy-search.html`
- HTTP 缓存标准：`https://www.rfc-editor.org/rfc/rfc9111.html`
- MDN 条件请求：`https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/If-None-Match`
